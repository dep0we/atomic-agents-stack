# Control-layer positioning

Atomic Agents is a portable agent framework. It owns the controls that define an agent's state, action boundary, authority, cost, and audit trail. It leaves deployment infrastructure, enterprise data governance, caller identity, payment execution, and centralized operations to the operator. The default filesystem implementation is usable on one machine; backend Protocols provide seams for other substrates. See [architecture](architecture.md) for the runtime and vault model and [protocols-shipped](protocols-shipped.md) for the current backend inventory.

## Control-surface map

| Control surface | Atomic Agents position | Where the operator brings their own |
|---|---|---|
| **Runtime: where the agent runs** | Runtime agnostic. The vault, or a backend's canonical exported shape, carries agent state; the runtime and storage substrate can be selected independently. | Cron, launchd, a skill runner, embedded Python, an HTTP service, containers, or an orchestration platform. The [serve spec](spec/37-serve.md) deliberately leaves perimeter controls to that environment. |
| **Data governance: what data means here** | The framework governs agent state: markdown configuration, frontmatter, provenance where represented, memory version snapshots, and the JSONL audit trail. | Governance for enterprise records remains in the operator's data layer. Atomic Agents does not replace a warehouse, CRM, customer database, row-level access system, retention program, or data catalog. |
| **Identity: who is the principal** | `persona/IDENTITY.md` declares the agent's identity. [Mandates](spec/29-mandates.md) record durable, scoped authority, and [PrincipalBackend](spec/48-principal-backend.md) maps already-verified claims to a principal at the framework boundary. | Human-user identity, OAuth or OIDC flows, token verification, and delegated-token storage belong to the operator's identity perimeter. PrincipalBackend intentionally consumes claims already verified there; it does not act as an identity provider. |
| **Action classification: what can it do without approval** | This is framework-owned. [The judge layer](spec/28-judge-layer.md) defines `read_only`, `reversible_write`, `external_side_effect`, and `high_risk`, with default policy by class and allow, block, revise, or escalate outcomes. | The operator declares the available tools and their classifications in `tools.md` and `mcp.md`, and chooses whether to enable and configure the judge. An unclassified tool defaults to `external_side_effect`. |
| **Cost authority: what can it spend** | Cost guardrails run before model work and across the call tree. [Mandates](spec/29-mandates.md) can add durable token and external-cost limits and escalation thresholds. | Payment rails and settlement remain outside the framework. A tool may report an external cost, while the operator's payment processor or approval system executes and reconciles the charge. |
| **Observability: which events are logged** | Each run has a JSONL audit record with a `run_id`; helper, tool, and delegate records link through `parent_run_id`. The dashboard and judge decision records build on that trail. [LogBackend](spec/22-log-backend.md) and [canonical export](spec/40-canonical-export.md) provide the storage and portability seams. | Operators choose whether to forward records to a centralized log, trace, or monitoring service and own its retention, alerting, access, and incident workflow. The framework's log backend accepts alternate sinks without making one vendor the default. |
| **Kill switch: who can stop it** | The framework provides layered refusal and suspension controls through locks, mandates, cost budgets, tool and policy decisions, and judge escalation. These controls can prevent the next action and preserve the reason in the audit trail. | Stopping the process, pod, container, host, or service belongs to the operator's runtime and operations layer. The framework does not claim to replace process supervision or infrastructure termination. |

## What operators need to provide

A filesystem-default deployment needs no external control plane to run a single local agent. As the deployment grows, operators add the environment-specific pieces at the corresponding seam: a runtime and perimeter, an identity provider, enterprise data controls, payment execution, and a log or trace destination. The framework keeps the agent files and control semantics consistent while those integrations change.

This division is intentional. The framework's Protocol pattern lets an alternate backend register without forking core; the filesystem implementations remain the reference path. Read [spec/20 — MemoryBackend](spec/20-memory-backend.md) for the pattern, [spec/32 — PolicyBackend](spec/32-policy-backend.md) for fleet-wide settings, and [spec/27 — doctor](spec/27-doctor.md) for deployment checks.
