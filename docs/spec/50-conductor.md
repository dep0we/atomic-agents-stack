## Overview

A **conductor** runs a multi-stage **playbook** — an ordered, human-gated process — to completion, and **never loses its place**. If a run stops mid-process (crash, restart, or a gate left awaiting a human decision for hours or days), it resumes exactly where it left off with all prior state and rulings intact.

The conductor is **not** a backend protocol and **not** a graph/workflow engine (LangGraph stays out of scope per ROADMAP §"What we're NOT building"). It is an **orchestration layer** in the spirit of `agent.call()` and the goal-outcome coordinator (`goal/coordinator.py`, spec/41): a thin sequencer that composes primitives the framework already shipped, plus **one new artifact** — the gate-decision record.

The conductor's durable state **is a decision ledger**. The resume cursor and the audit record are the same artifact: every stage entered/completed and every human gate decision is written as *what was decided, by whom, why, when, and what is still pending*. That single artifact gives both:

- **suspend and resume** mid-playbook (the protection property), and
- later **query** — "what did we decide at the security gate for feature X, and why" (the audit property).

This is a direct application of Principle #5 ("audit trail is structural"): a rationale-bearing, append-only, rolls-up record is exactly the structural audit the framework already values. The conductor does not invent a new audit shape — it **leans on the goal ledger**, which is already append-only, CAS-guarded, and exportable (spec/41).

## Why now (the gap is known, not speculative)

Durable pause/resume across a long, gated run is table-stakes for the org half of the throughline ("a home user with one agent and an org with a fleet"). The framework already *committed* to resumable runs when it shipped **Goal (#425)**, **Outcome (#426)**, **Queue (#428)**, and **Idempotency (#520)** — those backends only make sense if long runs survive interruption. The conductor is the missing layer that ties them into one named, coherent capability. Leaving it unnamed forces every operator to re-wire it by hand, which violates the gracefulness aesthetic ("things that should be easy are easy; defaults are right").

Independent corroboration: the **dev-process-kit** repo (the first real playbook the conductor must run — see §"Reference playbook") scatters its gate decisions across three disconnected places (`docs/DECISIONS.md`, per-build Tier-A rulings JSON, and per-gate receipts) with **no unified, durable, queryable record of every human gate decision with its rationale**. Different vantage, same gap reasoned to abstractly. The conductor's decision ledger is the unified record that closes it.

Per [[feedback_dont_defer_known_architectural_gap]]: durable resume is a *known, load-bearing* org requirement, not a speculative cliff. The shipped primitives (Goal/Outcome/Queue/Idempotency) only fully make sense *because of* the conductor. So the conductor is designed first-class now, knowing the resume + ledger requirement from line one — not retrofitted.

## Vocabulary

| Term | Meaning |
|------|---------|
| **Playbook** | An ordered definition of stages: what to run at each step, which model, and where execution must stop for a human decision. A vault-native markdown artifact (see §"Relationship to spec/18"). |
| **Stage** | One step of a playbook. Either an **automated stage** (an `agent.call()` / `outcome` run / single `delegate`) or a **gate**. |
| **Gate** | A stage that halts execution awaiting an external (human) decision before the run may continue. |
| **Conductor run** | One execution of a playbook against one work subject (e.g. "run the dev-process-kit playbook for feature #1234"). Has a stable `conductor_run_id`. |
| **Decision ledger** | The durable record of every stage transition and every gate decision for a run. **It is the goal ledger** (spec/41) — `goal.md` history + `goal_history.jsonl` — plus the new gate-decision event type. Resume cursor and audit record in one. |
| **Gate-decision record** | The one genuinely new artifact: a structured record of a pending-or-answered human decision (`{decision_id, stage_id, prompt, options, context_ref, held_conflict_keys, disposition, answer, answered_by, answered_at, rationale}`). There is **no** `status` field — `disposition is None` encodes "pending" and the gate sub-goal's goal-ledger STATUS is the durable cursor (D2). |

## The composition — how the conductor maps onto the five shipped primitives

The conductor is a sequencer. Every piece of durable state it needs **already exists** in a shipped primitive. The design discipline (Principle #3 "compose, don't merge"; "pick fewer concepts") is to add the *minimum* new concept — one record type — and route everything else through existing stores.

| Conductor concept | Shipped primitive it maps to | Notes |
|-------------------|------------------------------|-------|
| The run's durable anchor + ordered stages + append-only history | **Goal (spec/41)** | One conductor run **is a goal**. `goal.intent` = "run playbook X for subject Y". Each stage **is a sub-goal** (`pending → in_progress → complete/blocked/abandoned`). `goal_history.jsonl` is the append-only ledger; `apply_transition()` (CAS-guarded, MUST 10) is the atomic stage-transition primitive. `archive_goal()` retires a finished run; `list_archived()` enumerates past runs. |
| Each automated stage's persisted result | **Outcome (spec/42)** | An automated stage that iterates-to-rubric persists its terminal result as `result.json` (write-once, MUST 9). The **goal-outcome coordinator** (`dispatch_sub_goal_as_outcome`, spec/41) already composes Goal+Outcome for the *single*-stage case with a fail-closed cost gate + CAS terminal transition. **The conductor is that coordinator generalized across N stages.** |
| Don't re-run a stage that already completed on resume | **Idempotency (spec/45)** | `agent.call(idempotency_key=…)` is already wired (W1–W8). The per-stage key is deterministic, so a resume that re-dispatches a completed stage short-circuits (COMPLETED → deduped) instead of re-spending. See §"Resume semantics" for the exact role idempotency plays vs the ledger. |
| (a) The pending stages when a stage fans out to a role team, AND (b) serializing a conflicting run behind a suspended gate | **Queue (spec/44)** — **conditional composition** | Two uses. (a) *Role-team fan-out:* a stage dispatching work to multiple roles uses the project-scoped QueueBackend (org shape). (b) *Conflict serialization:* a new run that needs a resource a gate-suspended run holds writes an **advisory** record to a **per-agent** QueueBackend bucket keyed by the blocking decision and self-releases on its own next `run()` invocation (see §"Concurrency and conflict serialization" — serialization correctness rides on the conflict-scan lease + the goal ledger, not on the advisory queue). Queue is absent only when a playbook declares no role-team dispatch AND no conflict keys (the simplest single-job-at-a-time home case); the moment overlapping runs can conflict, the conflict-scan-lease + ledger serialization mechanism engages (with the advisory queue as its audit breadcrumb). |
| Cost ceiling across the whole (possibly multi-day) run | **Tree-cap** | The conductor run is the cost root. Each stage's `agent.call()` / `outcome` / `delegate` clamps to `MIN(stage_remaining, run_remaining − stage spend so far)` — identical to delegation (spec/15) and the goal-outcome coordinator's pre-dispatch gate. The run cap binds at each iteration boundary (the threaded headroom is decremented by the stage's own accumulating spend), so within-stage overshoot is bounded by one iteration's spend — the same per-call granularity as the delegate tree-cap. |

**The conductor itself is a thin orchestrator** — a free function / module (like `goal/coordinator.py`), **not** a backend Protocol and **not** an agent. It holds no authoritative state of its own; every durable fact lives in Goal / Outcome / (optional) Queue / Idempotency. Kill it mid-run, restart it, and it reconstructs its place entirely from those stores.

## The one genuinely new artifact — the gate-decision record

Everything above is reuse. The single new concept is the **gate-decision record**: how a run durably says "I am blocked here, awaiting *this* human decision, and here is how to resume when the answer arrives."

Goal carries history but **not** a "blocked on external input, resume with this value" state. The existing sub-goal `blocked` status means *blocked by a sibling sub-goal* (`blocked_by` references another sub-goal that must reach `complete`) — it is not "awaiting a human answer to inject." That is the gap the gate-decision record fills.

### Shape (LOCKED for PR2 fields; PR3 adds concurrency)

```python
@dataclass(frozen=True)
class GateDecision:
    decision_id: str              # stable id for this gate within the run
    stage_id: str                 # the sub-goal/stage this gate guards
    prompt: str                   # the question put to the human (plain language)
    options: list[str]            # offered choices (may be empty for free-text)
    context_ref: str              # opaque ref to the run state the human reviews
    held_conflict_keys: list[str] # declared resources this suspended run holds
                                  # (e.g. ['merge:main']) — drives conflict
                                  # serialization; see §"Concurrency and conflict
                                  # serialization". Empty when the run declares none.
    # Typed gate ruling — 'continue' (proceed), 'skip' (skip stage), 'halt' (stop run).
    # DISTINCT typed field — NOT magic-word-sniffed from the free-text answer string
    # (gate-answer-semantics ruling, PR2 #581). None while pending.
    disposition: Literal['continue', 'skip', 'halt'] | None
    answer: str | None            # the human's free-text answer (None while pending)
    answered_by: str | None       # principal.identifier of the human who ruled (spec/48)
    answered_at: str | None       # ISO 8601 wall-clock of the ruling
    rationale: str | None         # WHY — the load-bearing audit field
```

Note: the pre-PR2 DRAFT spec listed a `status: Literal['pending', 'answered']` field. This was removed in PR2 — the resume cursor is the gate sub-goal's STATUS in the goal ledger (via `apply_transition`), not a field on the GateDecision object itself. `GateDecision.disposition is None` effectively encodes "pending"; a non-None disposition encodes "answered." The goal-ledger status (`awaiting_decision` / `complete` / `skipped` / `abandoned`) is the durable machine state; `GateDecision` is pure audit.

`answered_by` ties into PrincipalBackend (spec/48) so the ledger records *who* ruled, not just *what* — the org-shape audit property. For the home shape it is `LOCAL_PRINCIPAL`.

### Suspension and resume (the new control-flow bit)

A conductor run that reaches a gate:

1. Writes a `conductor_gate_pending` event (a `GateDecision` with `disposition=None`) into the ledger (a new `goal_history` event type — RULED OD1a/OD2), and transitions the gate stage's sub-goal to a new **`awaiting_decision`** suspension status with the `decision_id` recorded in `gate_decision_id` (RULED OD1a). The sub-goal status + `gate_decision_id` are the durable resume cursor; the event is pure append-only AUDIT (so the cursor survives even a crash before the audit event lands — the re-surface reconstructs the pending `GateDecision` from the durable status + the fingerprint-pinned playbook gate stage and HEALS the missing audit event, P0-1).
2. **Returns control.** `conductor.run(...)` returns a `ConductorState` carrying `status='awaiting_decision'` and the pending `GateDecision`. No thread is parked; no resource is held across the (possibly multi-day) wait. The run is *durably suspended*, not *blocking*.
3. When the human answers, the operator calls `conductor.resume(conductor_run_id, decision_id, answer, rationale, principal)`. The conductor:
   - re-reads the ledger to confirm the run is still suspended on `decision_id` (rejects a stale/duplicate answer),
   - appends the `conductor_gate_answered` event (a `GateDecision` with the typed `disposition` + `answer`/`answered_by`/`rationale`) — audit + the injected value, in one record (embedded as the `apply_transition` `history_event`, transition-first per spec/41 MUST 6),
   - transitions the gate stage off `awaiting_decision` (clearing `held_conflict_keys`), injects the answer at exactly that stage, and continues the playbook from the next stage. `resume()` does **not** push-release runs queued behind this decision; a queued run self-releases on its own next `run()` invocation once this gate leaves `awaiting_decision` (see §"Concurrency and conflict serialization").

The answer is injected *at the gate point* because the ledger records *which* `decision_id` the run was suspended on — the resume cursor and the injected value are the same record. This is the property the issue calls out: the resume cursor and the audit record are one artifact.

**`skip` vs `continue` are runtime-identical in PR2 (H3 — honest scope).** Both dispositions proceed to the next stage; the ONLY difference is the gate's own recorded audit status — `'skipped'` vs `'complete'`. Neither skips a downstream *guarded* stage. This is acceptable for PR2 (a gate is a decision point, and `'skipped'` is the honest audit label for "the human chose not to endorse this gate's work"), but it is documented explicitly so the equivalence is not mistaken for a richer control-flow feature: stage-level *skip-the-guarded-work* remains deferred (tracked in #671); the #584 reference playbook uses `skip` as a runtime-identical audit label, consistent with this deferral. The control flow is the same; only the audit label differs.

## Resume semantics — the ledger is primary, idempotency is the safety net

Resume must be correct across two failure modes, and they use different mechanisms. Getting this boundary right is the load-bearing design statement of the spec.

**The goal ledger is the authoritative resume cursor.** On (re)start, the conductor reads the run's goal:

- A stage whose sub-goal is `complete` **and** whose result is resolvable from the durable store → **skip**; reuse the stored result. The result comes from the store, never re-computed. Resolution tries the sub-goal `output` pointer first, then **REPAIRS from idempotency** if the pointer is missing/unresolvable: a COMPLETED idempotency record carries a `prior_result_ref`, and if `OutcomeBackend.read_result(prior_result_ref)` resolves, the conductor re-stores the pointer and treats the stage as resolved-from-store (recovers from a crash that landed the result + idempotency commit but lost the pointer-write — instead of wedging the resume). **PR1 enforces the full C2 predicate (the result-presence half is not deferred):** a `complete` stage whose result is unrecoverable from **both** sources (no resolvable `output` AND no COMPLETED idempotency record with a resolvable `prior_result_ref`) is ledger corruption and **fails closed** (`GoalCorrupted`), never a silent skip.
- A stage that is `awaiting_decision` → re-surface the pending `GateDecision`; wait for `resume()`. **The re-surface reconstructs the pending `GateDecision` from the DURABLE status (P0-1):** `gate_decision_id` (goal.md) + the playbook gate stage spec (prompt, options — verified-identical by the structure fingerprint, see below) + a re-derived `context_ref` + `disposition=None`. It does **not** hard-require the `conductor_gate_pending` audit event — that event is written AFTER goal.md (apply_transition MUST 6 ordering), so a crash in that window leaves a durably-`awaiting_decision` sub-goal with no event. The re-surface HEALS the audit (re-appends the event) and proceeds, rather than raising `GoalCorrupted` (the event is pure audit, consistent with D2; only an `awaiting_decision` sub-goal with NO `gate_decision_id` — the durable cursor itself unreadable — is corruption).
- A stage that is `skipped` (gate answered with `disposition='skip'`) → terminal-done; treated as complete-with-no-result and NOT re-dispatched. **C3 symmetry:** a `skipped` stage MUST carry a recorded `conductor_gate_answered` (disposition='skip') ruling in the ledger — a `skipped` status with no such ruling is corruption and **fails closed** (`GoalCorrupted`), exactly as a `complete` stage with no resolvable result does. "A skipped stage is a recorded ruling, never an absent stage" (C4) is enforced on the resume path, not merely on the write path.
- A stage that is `pending` or `in_progress` → (re-)run it.
- A stage that is `blocked` (the coordinator's terminal mapping for max-iterations/failed) → normalize `blocked → in_progress` (CAS-guarded) and re-run it. `blocked` is conductor/coordinator-produced, so re-running is recovery.
- A stage that is `abandoned` → **HALT the run** (`halt_reason='stage_abandoned'`, a `conductor_run_halted` event carrying the `stage_id`) and return control to the operator. `abandoned` is **terminal on resume** — it is **never** auto-revived, because only a deliberate operator/external action sets it; auto-reviving it would let crash recovery override human control flow. Not a silent skip and not a normalization (maintainer ruling A, 2026-06-27).

**Cap-exhausted at a gate halts rather than surfaces it (C6).** A gate is a zero-cost human decision point, but the conductor's pre-suspension gate check still enforces the run cap: when a gate stage is reached and `run_remaining <= 0`, the run halts (`halt_reason='run_cap_exhausted'`) **before** the suspension is committed, rather than surfacing the pending `GateDecision`. This is the C6 "no conductor code path crosses the cost gate when the cap is exhausted" discipline applied uniformly — the suspension write itself is refused at the cap boundary. The operator sees a cap-exhausted halt, not a pending gate; lifting the cap (or starting a fresh run) is the path forward. (Letting a $0 gate suspend past an exhausted cap is a deferred refinement — it would require carving the gate suspension out of the uniform pre-stage gate.)

**Idempotency is the safety net for one narrow window** — a stage that committed its result but crashed *before* the ledger transition landed (the commit-then-crash-before-ledger-update window). A deterministic per-stage idempotency key (`conductor:<conductor_run_id>:<stage_id>`) means the re-dispatched stage's `begin()` sees COMPLETED and short-circuits (W7) instead of double-spending the LLM. **PR1 ordering note (impl reconciliation):** the PR1 conductor commits idempotency *after* the coordinator's terminal goal transition, so its own ordering never produces a COMPLETED idempotency record while the goal still reads `in_progress` — the goal-ledger skip (above) is the primary resume path, and the COMPLETED short-circuit branch in `run()` is a forward-looking defensive path for a future commit-before-transition ordering or a multi-host backend that can land COMPLETED ahead of the ledger.

**Two correctness facts that must be stated, not glossed:**

1. **A deduped Response carries no output** (spec/45 W2/W7 — `deduped_response()` returns `text=''`). So the conductor MUST take a replayed stage's *result* from the durable store (Outcome / goal sub-goal), **never** from the deduped Response. Idempotency is the *guard against re-spending*; the Goal/Outcome store is the *source of the result*. (This is a second reason the result lives in the shipped stores, not in a new conductor-invented store — RULED OD2.)

2. **The single-host hard-crash gap is real and bounded.** `FilesystemDedupLedger` is `supports_ttl=False` (spec/45). A *hard* crash mid-stage leaves the idempotency lease wedged IN_FLIGHT with no TTL sweep, while the goal sub-goal reads `in_progress`. The conductor's resume relies on the **ledger** (re-run an `in_progress` stage), and Outcome write-once (MUST 9, fresh `run_id` per attempt) keeps the re-run from corrupting state — at the cost of one extra stage run in this rare window (audit-visible, never silent). **Exactly-once across hard crashes requires the deferred IdempotencyBackend TTL sweep (spec/45 §"TTL sweep") or a multi-host Redis/Postgres IdempotencyBackend.** This is named here as a known limitation with a named dependency — the home/single-host shape accepts the bounded duplicate-spend; the org shape closes it by registering a TTL-capable backend. The conductor does not build the TTL sweep ahead of that need.

   **Run-cap UNDER-COUNT in the same window (bounded fail-OPEN, named not glossed).** Cumulative spend for the run cap is re-summed from the conductor goal's terminal `sub_goal_outcome_dispatched` events only. A stage that spent real LLM money but whose *terminal* event never landed — a hard crash mid-LLM-call before the coordinator's terminal `apply_transition`, OR a terminal-transition write that itself fails after `runner.run()` already spent — leaves that partial/whole spend uncounted toward `run_cap_usd` on resume (the spend went to the parent agent's model.md daily/monthly ledger, which the run-cap reader never consults). So a crash-resume cycle can re-spend the partial stage without it counting against the run cap. **Bounded:** the model.md daily/monthly cap on the parent agent's log still binds, so the exposure is material only for an operator who sets `run_cap_usd` while disabling those caps, and only across repeated hard crashes mid-call. Same single-host crash window as the duplicate-run fact above; a follow-up (cross-check the parent agent daily-log delta against the ledger on stage close/resume) is filed, not built ahead of need.

## Concurrency and conflict serialization

A gate-suspended run can be parked for hours or days. During that window the agent must keep doing its other work, and a *conflicting* second run must not barge past the pending decision. Three rules, in order of how often they fire:

1. **Suspension holds no agent lock (the common case).** A run suspended on a gate parks no thread and holds no `AgentLock` across the wait (Contract C8). So a new scheduled trigger (a cron tick, an HTTP call) for the *same agent* starts a fresh, independent conductor run and **proceeds normally**. The home expectation — "the agent is waiting on me for job one, but its scheduled job two still runs" — is the default behavior, not a special case.

2. **Non-conflicting concurrent runs proceed freely.** Each conductor run is its own goal (one run = one goal), so two runs never collide on the ledger itself. Absent a shared declared resource, they run fully in parallel under the agent's normal per-run locking.

3. **A conflicting run queues behind the decision (the new bit).** A run declares the resource(s) it needs — a **conflict key**, an opaque string the playbook author chooses (e.g. `merge:main`, `deploy:prod`, or a path the gated stage will write once the human answers). When a new run needs a conflict key that a *gate-suspended* run currently holds (recorded in that run's `GateDecision.held_conflict_keys`), the new run does **not** block-wait (that would wedge it for the multi-day gate) and does **not** barge. The detection is the load-bearing step: a `conductor-conflict-scan` LockBackend lease serializes the scan + suspend/queue decision across runs, and the new run records its queued state durably as a `conductor_run_queued` event in its own goal ledger. It also writes an **advisory** record to a **per-agent** QueueBackend bucket keyed by the blocking `decision_id` (spec/44) — an audit breadcrumb and a demonstration of the producer primitive, NOT the load-bearing serialization state; nothing dequeues it. **Release is self-release, not push-release:** `resume()` does NOT wake the queued waiters. The queued run re-checks the answered gate on its *own* next `run()` invocation (`_is_decision_still_pending`); once the gate is no longer `awaiting_decision`, the run self-releases (appends `conductor_queue_released`) and continues. This is the literal "flagged or queued up to run right after the human decision is made" behavior, advanced on the queued run's next scheduled tick.

**Why a held lock is the wrong mechanism, and Queue is the right one.** Holding a `LockBackend` lock across the gate would satisfy mutual exclusion but violate rule 1 — it wedges the agent for the entire (multi-day) human wait, starving every other job. Record-based serialization gives the same exclusion *without* holding a resource across the wait: the suspended run owns the conflict key by *record* (its `held_conflict_keys` in the goal ledger), not by a *held lock*, and the waiter's durable state is its own `conductor_run_queued` goal-ledger event (the per-agent advisory queue file is audit only), not a live thread. The suspension stays resource-free (C8) and the conflict still serializes correctly.

**Honest limits (named, not hidden):**
- **Conflict keys are declared, not inferred.** The framework cannot magically know two arbitrary jobs collide; the playbook author names the resource. An undeclared real conflict is not serialized — same discipline as any lock-scope design. The cost of the chosen behavior (vs. flag-only) is this declaration burden; the benefit is automatic clean sequencing instead of a hand-resolved collision.
- **This is the second reason Queue is load-bearing, not just org-shape fan-out.** Even a single home agent with two overlapping scheduled jobs hits conflict serialization, so the spec frames Queue as *conditional* (present when conflict/fan-out is possible), not *org-only*.

## Cost — the tree-cap across a multi-day run

Per Principle #4 ("cost is first-class"), every conductor stage runs behind a cost gate, and the *whole run* is capped. The conductor run is the cost root; each stage clamps to `MIN(stage_remaining, run_remaining − stage spend so far)`, exactly as delegation (spec/15) and the goal-outcome coordinator's pre-dispatch gate already do. The run cap binds at each iteration boundary — the per-iteration gate decrements the threaded run-level headroom by the stage's own accumulating spend, so within-stage overshoot is bounded by one iteration's spend (the same per-call granularity as the delegate tree-cap), not zero. A gate-suspended run that resumes days later resumes *under the same run-level ceiling* — the ledger carries cumulative spend, so the cap survives the suspension. **The ceiling itself is pinned, not re-read live:** `run_cap_usd` is recorded in the `conductor_run_started` ledger event **at run creation — written immediately after `create_goal()`, before any other run() work** — and read back from there on every `run()`/resume, so an operator who edits `run_cap_usd` in PLAYBOOK.md between a crash and a resume does **not** change the resumed run's cap (a fresh run pins `playbook.run_cap_usd`; an existing run reuses its run-start value). Emitting the pin at create (not in a later step) means it exists the instant `goals/<id>/` exists, closing the crash window where a resume could otherwise adopt the current edited cap. No conductor code path runs an LLM without passing through the stage's cost gate first (the gate fires *before* the stage's first LLM call, never after — same discipline as `_check_cost_guardrails`).

**The playbook STRUCTURE is pinned across suspend/resume too, not just the cap (P0-2).** Pinning only `run_cap_usd` protects cost but leaves control flow exposed: an operator editing `PLAYBOOK.md` during a multi-day gate suspension (changing a prompt or rubric ref, flipping `is_gate`, adding/removing/reordering stages) would silently change what the resumed run executes. So a **playbook fingerprint** — a stable hash of the ordered `(stage_id, is_gate, effective prompt, prompt_ref, options, rubric_ref)` tuples — is recorded in the `conductor_run_started` event at run creation (alongside `run_cap_usd`). On every `run()`/resume of an EXISTING run, the conductor recomputes the fingerprint from the LIVE playbook and **REFUSES** (raises a clear `playbook-changed` error) on mismatch. A multi-day run executes the playbook it started with. (A run started before P0-2 shipped has no pinned fingerprint → the check is skipped for backward-compat: a structure that was never pinned cannot be refused.) This also makes the P0-1 gate re-surface consistent — the gate stage spec it reconstructs from is verified-identical to the one that suspended.

**The cap must be a finite number.** A `run_cap_usd` of `.inf`, `.nan`, or `1e999` is **rejected at parse time** (`validate_playbook_manifest`): both `nan <= 0` and `inf <= 0` are False, so a bare `<= 0` gate would *accept* a non-finite cap and silently disable the run ceiling. The loader requires a finite value `> 0`. Symmetrically, a non-finite per-stage `total_cost_usd` in the ledger is treated as a **degraded** cumulative-spend read (which fails the run closed) rather than being summed — a `NaN`/`inf` event would otherwise poison `run_remaining = cap − total` (and `nan <= 0` is False, so the run would never halt).

**The per-iteration binding requires cost guardrails to be ON.** When the agent's `model.md` sets `cost_guardrails_enabled=false`, `_check_cost_guardrails()` short-circuits to *allow* before the parent-headroom clamp, so the threaded run-level headroom never gates a per-iteration call — the run cap degrades to the coarse **between-stage** `run_remaining <= 0` backstop alone (a single stage can overshoot the run cap by up to its own per-call spend). `run()` emits a **loud warning** when it detects guardrails are disabled, so the degradation is never silent (Principle #4/#13).

## PR1 hardening + known limitations

- **`stage_id` is validated at parse time, before any side effect.** A `stage_id` becomes the conductor sub-goal id *and* the per-stage idempotency-key suffix (`conductor:<conductor_run_id>:<stage_id>`), so it must match the goal-id charset (`[a-z0-9_-]`, 1–64 chars — no path separators, no `..`, no whitespace). `validate_playbook_manifest` REFUSES a malformed `stage_id` before any goal is created or any ledger event is emitted (a separator-bearing id would otherwise create the goal and emit `conductor_run_started`, then crash mid-run).
- **Single-writer per `conductor_run_id` (PR3, closed).** `run()` acquires a per-`conductor_run_id` `LockBackend` lease immediately after resolving the run ID. A concurrent `run()` call on the same ID receives `LockBusy` (the caller should retry after the executing invocation returns). The lock is acquired AFTER `conductor_run_id` is resolved so the lock key is stable; the whole run body is wrapped in a `try/finally` that calls `release()` on every exit path (normal return OR propagating exception). The lock is **not** released by garbage collection — the reference `FilesystemLockBackend` stores a raw fd int in `LockHandle.backend_state` and `LockHandle` has no `__del__`, so dropping the handle closes nothing; the explicit `finally release()` is required for correctness (a leaked lease would make the next in-process `run()`/`resume()` on the same id dead-lock with `LockBusy`). This closed the PR1 known gap where two concurrent `run()` calls could double-dispatch stages and defeat the tree-cap. (PR3 #582.)
- **Symlinked skill/playbook dirs are followed (T15).** Discovery (`skills._discover_entry_dirs`, shared by `discover_skills` and `discover_playbooks`) follows directory symlinks under `<agent_root>/skills/`, so an out-of-vault symlinked playbook dir IS discovered and run. This is the framework's pre-existing operator-trust model (TENSIONS T15: the agent folder is the trust boundary; what the operator symlinks under it is theirs to vouch for) and is **left unchanged** by the conductor work. Per-stage `prompt_ref`/`rubric_ref` resolution remains canonical-path-contained (`safe_resolve_under`); only top-level dir discovery follows symlinks.
- **Observe-later (#654).** The dashboard / `discover_agents` / `list_archived` surfaces do not yet enumerate conductor run-goals at `goals/<conductor_run_id>/` — same root cause as the already-filed **#654** (multi-goal addressing observability). Conductor runs are *observe-later*; the run is fully durable and queryable from its own `goal_history.jsonl` today, and #654 wires the fleet-observability surfaces.

## Relationship to spec/18 (Skills) — "a skill that leans on goals," refined

The design conversation framed the conductor as "a skill that leans on goals." That holds for **one** layer and diverges for the **other** — naming the split keeps a future contributor from collapsing them.

- **The playbook *definition* IS a skill-shaped artifact (the framing HOLDS).** A playbook — the ordered stages, each stage's prompt, the gate questions, the model dial per stage — is authored as vault-native markdown, progressively disclosed (Principle #6), editable in any text editor (Principle #7). It can live as a `SKILL.md`-shaped file the agent loads to know *what the process is*. "A skill that describes a multi-stage process" is exactly right for the definition.
- **The conductor *runtime* is NOT a skill (the framing DIVERGES).** The thing that *executes* the playbook — sequences stages, writes the ledger, suspends and resumes across days — is an orchestration layer in code, invoked programmatically (like `agent.call()` / the goal-outcome coordinator). A skill is *instructions loaded into a turn*; it cannot "return control and resume in three days." Only the runtime can.

This mirrors the issue's execution-model note exactly: the **kit-side** conductor (a Claude Code skill) is necessarily a *stateful guided checklist*, because in the Claude Code harness skills are instructions loaded into the turn, not functions that return control. The **atomic-agents** conductor is a *true orchestration engine*, because `agent.call()` is programmatic, `load_skill` is a real call, and goals/queue/outcomes are real state. The two conductors differ in **execution model**, not just "human present vs human remote." So: playbook definition = skill (markdown, vault-native, progressively disclosed); conductor runtime = orchestration layer (code). RULED OD4.

## Relationship to the management CLI (spec/54) — compose above, don't duplicate

> **Addendum, 2026-06-25.** spec/54 (Fleet Management CLI) did not exist when this DRAFT and its five rulings were written (2026-06-22). This section records where the conductor sits relative to it. It changes none of the ruled forks (OD1a–OD4); it names the composition seam and fixes the build order. An outside-voice review (cross-family, 2026-06-25) confirmed the layering and sharpened the seam — its points are folded in below.

The Agent Fleet Platform (epic #606) grows as **observe → manage → orchestrate → interact**. The console (#614/#615/#616) is *observe*; the management CLI (spec/54) is *manage*; **the conductor is *orchestrate*** — the durable, sequenced top of the manage layer; the chat UI is *interact*.

**The conductor composes *above* the management CLI; it does not overlap it.** They are different layers:

- The management CLI is the set of **verbs** — a single, synchronous, operator-present, validated+audited edit to one agent's config (`govern`, `set-model`, `apply-rec`). Its confirm (spec/54 S2 step 3) is in-the-moment; there is no suspend/resume.
- The conductor is the **sequencer** — a conductor stage MAY *be* "run a management verb" (an automated stage), the way an `agent.call()` stage invokes a tool. The conductor sits above the management CLI as `agent.call()` sits above tools.

So "run a playbook" is **not** a management verb (a single validated config edit). It is the orchestration layer that *invokes* management verbs and `agent.call()`s as stages. Neither layer subsumes the other.

**The reusable seam is the effect-execution contract, not the word "decision."** What a config-mutating conductor stage must reuse from the management CLI is its *safety envelope* around a config write — validate/authorize, preview, snapshot + rollback, atomic write, and the principal-stamped audit record (spec/54 S2 + M1–M10). A conductor stage MUST consume that envelope, never reimplement it. Concretely: a management verb's `--json` result (planned effect, validation outcome, snapshot ref, audit ref, applied result) is the structured stage-result the conductor consumes. This is the first-class reason to build the verbs first — they are the *transactional stage primitives* the conductor sequences.

**The human-decision seam — unify vocabulary, not storage semantics.** Both layers record "a human was asked X, chose Y — who, when, why." Keep that *audit vocabulary* consistent (principal-stamped, rationale-bearing) so a reader sees one decision language across both. But do **not** collapse them into one object. The management CLI's synchronous confirm is an inline consent event, not a durable, replay-aware `GateDecision`; forcing every `set-model` confirm through the goal ledger and a suspend/resume cycle would over-complicate the verbs for no gain (Principle #3). The conductor's `GateDecision` is the *durable, async* member of the family; the verb confirm is its *synchronous, in-process sibling* — shared vocabulary, different storage.

**Watch for rot — cursor vs. evidence.** This spec's headline ("the resume cursor and the audit record are the same artifact") holds **only** because the goal ledger is append-only and CAS-guarded (spec/41): the resume cursor is a **projection replayed over the append-only `GateDecision`/transition events**, never a mutable pointer overwritten in place. An operational cursor (mutable state) and immutable audit evidence have different lifecycles; the single-artifact design is safe *precisely because* the implementation derives the cursor from the immutable event stream rather than mutating a stored cursor. The build MUST hold that discipline — the moment a future change wants a mutable cursor field is the moment to split cursor from audit.

**Build order — the engine's real precursor is the GoalBackend, not the manage verbs.** The conductor *engine* (sequencer + durable ledger resume + gates + concurrency, #580–#583) depends on the GoalBackend addressing **one goal per conductor run** (one run = one goal, OD2). That was the engine's blocking precursor, and it shipped as **#642** (GoalBackend multi-goal addressing + `create_goal`, a versioned spec/41 RE-LOCK — merged 2026-06-27). The engine builds on it now. The management CLI verbs (#624 + `govern` #609, then `set-model`) are a predecessor only for the **config-mutating playbook stages**: a stage that edits an agent's config MUST consume a verb's effect-execution contract rather than reimplement it (see the seam above), which first matters when the dev-process-kit reference playbook (#584) is ported — NOT for the orchestration runtime. So: the engine is unblocked by #642 and builds first; the manage verbs gate later playbook *content*, not the conductor runtime. (An earlier draft of this addendum framed the verbs as the engine's predecessor; #580 discovery corrected it — the GoalBackend was the real cliff.)

## One-level delegation (#9) — the conductor is not a delegation level

A conductor runs stages; a stage may be an `agent.call()` that itself delegates to a specialist (spec/15). Does "a conductor running stages that delegate" stack onto the one-level delegation bound?

**No — and the bright line must be stated normatively.** One-level delegation bounds a single `delegate()` call tree: a coordinator delegates to a specialist; the specialist cannot delegate further. The conductor is **not** a delegation level. It is an orchestration layer that *sequences independent, fresh top-level agent runs* — there is no live parent call frame held across stages. Each stage starts a fresh call tree. Within a stage, an agent may delegate one level (coordinator → specialist). The conductor sequencing stage₁, stage₂, … does not deepen the call graph, exactly as cron running a delegating agent does not create two-level delegation, and the goal-outcome coordinator dispatching an `OutcomeRunner` (whose inner `agent.call()` may delegate) does not.

**The bright line (normative MUST — RULED OD3, guard upgraded to hard raise in PR4 #583):** the conductor is invoked at the orchestration top — by an operator, cron, serve, or a coordinator agent *before* it has delegated. A stage that is *itself* a delegated, depth-1 specialist call MUST NOT start or resume a conductor run. Allowing that would *launder* two-level delegation through the conductor (specialist → conductor → more delegating stages), defeating the #9 bound. Per OD3 as upgraded in PR4 #583, `run()` and `resume()` raise `ConductorLaunderRefused` (a `NestedDelegationRefused` subclass) when `agent.trigger == 'delegate'`, BEFORE any durable work. Full structural call-depth enforcement (refuse to start from within a delegate frame without the trigger signal) is deferred until a call-depth signal exists and is filed as [#665](https://github.com/dep0we/atomic-agents-stack/issues/665).

## Throughline — the SAME conductor runs a tiny home playbook and a big org playbook

The same conductor code runs both shapes. A 3-stage personal playbook (home — "draft → my review gate → publish") and the 13-stage dev-process-kit playbook (org) are the *same* stage-sequencing loop over the *same* Goal + Outcome + Idempotency stores. The differences are **backend registration** and **playbook size**, never a code fork.

The tradeoffs to name (per the throughline rule — neither shape is a degraded mode):

- **Queue is optional composition, so the home shape is not taxed.** At org scale, a stage that fans work to a role team uses the project-scoped QueueBackend (spec/44). At home scale, stages run inline on the one agent and Queue is entirely absent — the home conductor never instantiates queue machinery, leases, or claim logic. A stage declares a role-team dispatch or it doesn't; the conductor only reaches for Queue when it does. This keeps the home shape graceful (no concept it doesn't use) and the org shape first-class (real cross-host claim when it does fan out), rather than making one an inline-only degraded version of the other.
- **The ledger scales via the shipped GoalBackend swap, not a new store.** One conductor run = one goal. The home shape runs it on `FilesystemGoalBackend` (a few sub-goals, a short history — graceful). A big org playbook (many stages, possibly concurrent runs, long history) stresses the single-goal-per-agent, single-file model — and that is *exactly* what the GoalBackend Protocol's Postgres swap exists to absorb (spec/41 operator override; T15 / Position B). So the org shape scales by registering a Postgres GoalBackend, not by the conductor growing a parallel ledger store. The honest cost: a very large run's `goal.md` is bigger than a home goal — acceptable on filesystem for home, absorbed by the backend swap for org. This is the throughline working as designed: same conductor, different backend registration.
- **Exactly-once resume favors the org shape only where the org shape pays for it.** The single-host hard-crash duplicate-spend window (§"Resume semantics") is bounded and audit-visible for the home shape; the org shape closes it by registering a TTL-capable / multi-host IdempotencyBackend. Neither shape is broken; the stronger guarantee rides on the stronger backend the org shape already wants for other reasons.

## Conductor Contract (C1–C9 — normative, LOCKED)

These are the requirements an implementation MUST satisfy. The forks are ruled (§"Ruled decisions"); these MUSTs reflect those rulings. The reference implementation matches and the conformance suite passes (PR4 [#583](https://github.com/dep0we/atomic-agents-stack/issues/583)), so these MUSTs are now normative and LOCKED.

- **C1 — The conductor holds no authoritative state of its own.** Every durable fact (run anchor, stage status, stage result, gate decision, cumulative cost) lives in a shipped primitive (Goal / Outcome / Idempotency / optional Queue). Killing and restarting the conductor MUST reconstruct the run's place entirely from those stores.
- **C2 — The goal ledger is the authoritative resume cursor.** Resume MUST consult stage status in the goal, not the idempotency lease, to decide skip-vs-rerun. A `complete` stage with a resolvable stored result is skipped (result from the store; a `complete`-but-missing/unresolvable-result stage fails closed as corruption; gate stages marked `complete` via a `continue` ruling skip the result-pointer resolution — they have no outcome_run_id); a `skipped` stage (gate answered with `disposition='skip'`) is terminal-done and treated as complete-with-no-result (not re-dispatched); an `in_progress`/`pending` stage is (re-)run; a `blocked` stage is normalized and re-run (coordinator-produced); an `awaiting_decision` stage re-surfaces its pending `GateDecision`. An `abandoned` stage is **terminal on resume** — the run HALTS (`halt_reason='stage_abandoned'`) and is NEVER auto-revived, because only a deliberate operator/external action sets `abandoned`; reviving it would let crash recovery override human control flow (maintainer ruling A, 2026-06-27).
- **C3 — A replayed stage's result comes from the durable store, never from a deduped Response.** (Deduped Responses carry no output — spec/45 W2/W7.)
- **C4 — Every gate writes a rationale-bearing `GateDecision`; a skipped stage is a recorded ruling, never an absent stage.** "What is still pending" MUST be queryable from the ledger so a silent skip is structurally impossible (Principle #5; the kit's "never skip silently" rule).
- **C5 — `resume()` is idempotent and stale-safe.** A second answer to an already-answered `decision_id`, or an answer to a run no longer suspended on that decision, MUST be rejected without advancing the run (CAS against the ledger, reusing goal `apply_transition`'s `expected_from_status` guard, MUST 10).
- **C6 — Every stage runs behind a cost gate; the run is tree-capped.** No conductor code path runs an LLM without the stage's cost gate firing first. The run-level cap is threaded into the stage as `parent_remaining_headroom_usd` and decremented per iteration by the stage's own accumulating spend, so it binds at each iteration boundary (within-stage overshoot bounded by one iteration's spend — the delegate tree-cap granularity), with the coarse between-stage `run_remaining <= 0` halt as backstop. The cap survives gate suspension across days (cumulative spend carried in the ledger). **Named bound — the per-iteration binding requires `cost_guardrails_enabled`.** The per-iteration binding of `parent_remaining_headroom_usd` holds when the agent's cost guardrails are enabled; with guardrails disabled, `_check_cost_guardrails` short-circuits to `allow=True` *before* the headroom clamp (run.py M1), and the run cap degrades to the coarse between-stage `run_remaining <= 0` backstop — within-stage overshoot is then bounded only at the stage boundary, not per iteration. run.py warns loudly on this M1 degradation (Principle #4 / #13).
- **C7 — The conductor is not a delegation level.** A stage may delegate one level (spec/15); a depth-1 delegated specialist MUST NOT start or resume a conductor run. Calling `run()` or `resume()` when `agent.trigger == 'delegate'` MUST raise `ConductorLaunderRefused` (a `NestedDelegationRefused` subclass — NOT `ConductorError`) BEFORE any durable work (no goal created, no ledger event emitted, no gate answer recorded). The guard is keyed on the observable `trigger == 'delegate'` signal; structural call-depth enforcement (refusing a launder when the trigger signal is absent) is deferred to a follow-up issue (filed as [#665](https://github.com/dep0we/atomic-agents-stack/issues/665)). (RULED OD3: PR4 #583 upgraded the guard from `warnings.warn()` to hard raise.)
- **C8 — Suspension holds no live resource.** A gate-suspended run parks no thread, holds no lock across the wait, and is reconstructable purely from durable state. A new scheduled trigger for the same agent MUST be able to start and run an independent conductor run while a prior run is gate-suspended.
- **C9 — Conflicting runs serialize by record, not by held lock.** A run owns its declared conflict keys by ledger record (`GateDecision.held_conflict_keys`), never by a lock held across the gate. A new run needing a key held by a gate-suspended run MUST record a durable queued state (a `conductor_run_queued` goal-ledger event, under the shared `conductor-conflict-scan` lease that serializes scan+suspend/queue across runs) rather than block-wait or barge; an advisory per-agent QueueBackend record MAY be written as an audit breadcrumb but is NOT the load-bearing state. Release is **self-release**: a queued run MUST re-check the blocking gate on its own next `run()` invocation and self-release (append `conductor_queue_released`, continue) once that gate is no longer `awaiting_decision`; `resume()` MUST NOT push-release other runs. A run that declares no conflict keys is never serialized this way. The `conductor-conflict-scan` lease + the `conflict_keys` record serialize **within a single host only** — `conflict_keys` is NOT a distributed lock; cross-host mutual exclusion requires a multi-host-capable backend (§"Concurrency and conflict serialization").

> **Named exactly-once limit (qualifies C1, C5, C6).** The single-host hard-crash duplicate-spend / run-cap under-count window (§"Resume semantics", points 2–3) bounds the "reconstruct the run's place entirely" (C1), "idempotent and stale-safe" (C5), and "cost-capped" (C6) guarantees whenever the registered IdempotencyBackend is `single_host_only=True` / `supports_ttl=False` (the reference `FilesystemDedupLedger`). Root cause: spec/45's `begin()`→`commit()` hard-crash window with no TTL sweep — a hard crash between `begin()` and `commit()` leaves the lease wedged `IN_FLIGHT` with nothing to expire it. The org shape closes the window by registering a TTL-capable / multi-host IdempotencyBackend — tracked as [#585](https://github.com/dep0we/atomic-agents-stack/issues/585) (FilesystemDedupLedger TTL sweep) and [#526](https://github.com/dep0we/atomic-agents-stack/issues/526) (Redis/Postgres IdempotencyBackend). The home shape accepts the bounded, audit-visible window; neither shape is silently broken (Principle #13).

## What this is NOT (scope discipline — do not build ahead of the reference playbook)

- **Not a backend protocol** — the conductor adds no 22nd Protocol; it composes existing ones. (The gate-decision record is a new *event type in the goal ledger*, not a new store — RULED OD2.)
- **Not a graph/workflow engine** — no DAGs, no conditional branching, no parallel stage topologies. Stages are an ordered sequence. (LangGraph's territory, ROADMAP §"What we're NOT building".)
- **Not sub-playbooks / nested conductors** — a playbook is one level of stages. (Mirrors the one-level constraints, Principle #9.)
- **Not a playbook-authoring GUI** — playbooks are markdown (Principle #7).
- **Not the TTL sweep** — exactly-once-across-hard-crash rides on the deferred spec/45 TTL sweep or a multi-host backend; the conductor does not build it ahead of the org shape needing it.

## Ruled decisions (maintainer, 2026-06-22)

The five Tier-A forks were ruled by the maintainer. The contract above reflects these rulings.

**OD1a — Pending-decision record placement → RULED: in the goal ledger.** The `GateDecision` record is a new event type in the run's goal history (one store, alongside every stage transition). Rejected: a separate sidecar file next to `goal.md`, which would split "what's pending" from "what happened" and start down the scattering path the conductor exists to fix.

**OD1b — Conflicting-run handling → RULED: queue behind the decision.** A run declares the resources it needs (conflict keys). A new run needing a key a gate-suspended run holds records a durable queued state behind that decision (a `conductor_run_queued` goal-ledger event + an advisory per-agent QueueBackend breadcrumb) and **self-releases on its own next `run()` invocation** once the blocking gate is answered — `resume()` does not push-release waiters (see the §582 PR3 addendum for the as-built self-release model). Non-conflicting runs proceed freely; the suspended run holds no lock across the gate. Rejected: flag-only/optimistic (let both run, flag the collision for manual resolution) — it leaves a hand-resolved collision and a wasted spend instead of clean automatic sequencing. Rejected (off the table): a held lock across the gate — wedges the agent for the multi-day wait. This ruling is why Queue is *conditional*, not *org-only* composition — see §"Concurrency and conflict serialization".

**OD2 — Ledger storage → RULED: reuse Goal history + Outcome.** No 22nd backend, no parallel store. Goal history is already append-only, CAS-guarded, exportable, and doctored; big org runs scale via the shipped GoalBackend Postgres swap (spec/41 operator override), not a new store.

**OD3 — One-level delegation enforcement → RULED: document + best-effort guard now.** The bright line (a depth-1 delegated specialist MUST NOT start or resume a conductor run — Contract C7) is stated normatively. PR4 #583 upgraded the guard from `warnings.warn()` to `ConductorLaunderRefused` raise on both `run()` and `resume()` for the observable `trigger == 'delegate'` case, closing the OD3 "best-effort guard now" ruling for the raise-vs-warn question. Full structural call-depth enforcement (refusing a launder when the trigger signal is absent) is deferred until a call-depth signal exists and is filed as [#665](https://github.com/dep0we/atomic-agents-stack/issues/665). The launder path via `trigger == 'delegate'` is now a hard refusal; the remaining structural gap is documented, not silently ignored.

**OD4 — spec/18 boundary → RULED: confirm with a refinement.** The playbook *definition* is a skill-shaped artifact (markdown, vault-native, progressively disclosed); the conductor *runtime* is an orchestration layer in code, not a skill, because a skill cannot return control and resume across days. See §"Relationship to spec/18".

## Versioned normative addendum — #582 PR3 (2026-06-27): concurrency + conflict serialization

This addendum records the implementation contracts shipped in PR3. The concurrency/conflict design spec above (§"Concurrency and conflict serialization") was already published; this section records what was built.

### Per-run LockBackend serialization

`run()` acquires `agent.lock_backend.scope("conductor-runs").acquire(conductor_run_id, timeout=0.0)` immediately after resolving the `conductor_run_id`. The timeout=0.0 makes the acquire non-blocking: a concurrent invocation that already holds the lease receives `LockBusy` from the backend, which `run()` re-raises with a clear message. The entire run body runs inside a `try/finally`; the `finally` calls `_run_lock_backend.release(_run_lock_handle)` on every exit path (normal return OR propagating exception). Release is **explicit**, not GC-driven: the reference `FilesystemLockBackend` stores a raw fd int in `LockHandle.backend_state` and `LockHandle` defines no `__del__`, so dropping the handle would close nothing and leak both the fd and the held OS `flock` until process exit. A leaked lease would make the next `run()` on the same id dead-lock with `LockBusy` (the deferred→poll re-entry is a second sequential `run()` on the same `conductor_run_id` — an external caller re-invocation, NOT in-code recursion). `resume()` does NOT acquire the `conductor-runs` lease, so it is not blocked by a leaked `run()` lease — its stale/duplicate safety rides on the inner `apply_transition` CAS, not this per-run lease. The explicit `finally release()` is still a correctness requirement, not a cleanup nicety. All conductor run transitions are therefore single-writer-per-run at the process level.

### conflict_keys field on StageSpec and PLAYBOOK.md

Gate stages (is_gate: true) may declare `conflict_keys: [key-a, key-b]` in the embedded YAML block. These appear as `StageSpec.conflict_keys: tuple[str, ...]`. Rules:
- `conflict_keys` MUST NOT appear on automated stages (raises during `validate_playbook_manifest`).
- Each key MUST be non-empty, max 128 chars, no path separators, no null bytes.
- `conflict_keys` are included in the playbook fingerprint (so editing them on a suspended run raises `playbook-changed`).

### Conflict detection: scan+suspend under a shared conflict-scan lease

The double-suspend hazard. The per-run lock above serializes invocations of the **same** `conductor_run_id`, but two **different** runs hold **different** per-run leases and so do not exclude each other. If both reached a gate sharing a conflict key at the same instant, each could scan (seeing no conflict, because neither has written its `awaiting_decision` claim yet) and both suspend — two active gates holding the same key, the exact outcome conflict serialization is meant to forbid.

PR3 closes this by making the **scan + the suspension write a single critical section serialized across runs**: when `stage.conflict_keys` is non-empty, `run()` acquires a SINGLE shared lease `agent.lock_backend.scope("conductor-conflict-scan").acquire("scan", timeout=30s)` and holds it across `_scan_active_conflicts(...)` AND the `apply_transition(awaiting_decision)` write, releasing in a `finally`. A second run blocks on `"scan"` until the first releases, by which time the first's claim is durable, so the second's scan observes it and the second queues instead of suspending.

A single **global** key (`"scan"`), not a per-keyset digest, is required: two runs conflict iff their key SETS overlap, but overlapping sets can hash to different digests (`{a,b}` vs `{b,c}`), so only one shared lock guarantees mutual exclusion across any overlap. The brief over-serialization of disjoint-key scans is acceptable (the critical section is one scan + one write; a 30s bounded wait converts a stuck holder into a loud `LockBusy`).

`_scan_active_conflicts(agent, stage.conflict_keys, own_conductor_run_id)`:
1. Calls `agent.goal_backend.list_goals(agent.name)` to enumerate all active goals.
2. For each goal ID (skipping own), calls `for_goal(id).load_goal()` to read the sub-goals.
3. Returns `(blocking_run_id, blocking_decision_id)` if any sub-goal is `awaiting_decision` with `held_conflict_keys` that intersect the stage's keys; otherwise `None`.

**Degradation posture (fail-closed under a goal-backend read failure).** The scan runs ONLY for a conflict-keyed stage, and it **fails closed**: if `list_goals()` raises, or if any per-goal `for_goal(id).load_goal()` raises for a goal that might hold an overlapping key, the scan raises `ConductorConflictScanError` and `run()` aborts **before** executing the exclusive stage. The rationale is the inverse of the old fail-open posture: an unreadable goal *might* be holding the conflict key, so treating it as "no conflict" would let a new run execute the declared-exclusive stage concurrently with a holder it could not read — a silent mutual-exclusion violation. Failing closed instead refuses to proceed and lets the next scheduled trigger retry (`run()` is re-entrant/idempotent; nothing is half-written because the refusal happens before the stage dispatch and before the `awaiting_decision` claim). This aligns conflict serialization with the framework's fail-closed cost-read posture (#495/#497/#498) — an untrustworthy read refuses the privileged action rather than admitting it. A run that declares **no** conflict keys never triggers the scan and is never affected (the home shape is untouched). **Honest limit (blast radius):** `_scan_active_conflicts` raises `ConductorConflictScanError` if ANY goal in the agent's goal universe is unreadable — even one wholly unrelated to the declared conflict keys — because the scan cannot distinguish "might hold the key" from "unrelated" without reading the goal first. A single corrupt / legacy / unreadable goal can therefore wedge **all** conflict-keyed conductor runs for that agent until it is repaired (the deliberate A2 fail-closed posture, traded against blast radius). Scoping the scan to conductor-run `goal_ids` so an unrelated goal read-failure cannot wedge the conflict-keyed fleet is filed as a future optimization in [#663](https://github.com/dep0we/atomic-agents-stack/issues/663). **Remaining honest limit (multi-host):** the scan + the conflict-scan lease serialize correctly within a single host. Across hosts, two machines running the same agent against a `single_host_only` QueueBackend can still both pass their (locally-clean) scans and both suspend holding the same key — fail-closed closes the *read-error* hole, not the *cross-host* one. Operators needing hard cross-host mutual exclusion of a shared external resource must use a multi-host-capable backend (see §"Single-host capability honesty"); `conflict_keys` is not a distributed lock.

### Advisory conflict queue (write-only / audit)

If a conflict is found (still holding the conflict-scan lease), `run()`:
1. Enqueues an advisory record via `enqueue()` on the per-agent conflict queue — `role=<blocking_decision_id>` (the blocking gate's decision_id, e.g. `gate-<hex>`, NOT a fixed literal), `item_name=<sanitized conductor_run_id>` (the `crun-<uuid>` shape; the conductor defensively replaces any `:` with `-` and falls back to a sha256 hash if validation fails), payload = advisory JSON.
2. Appends a `conductor_run_queued` ledger event.
3. Returns `ConductorState(status='deferred', queued_behind_decision_id=<id>, queued_behind_conductor_run_id=<run_id>)`.

The advisory record is **write-only / audit** — nothing dequeues it, and it is explicitly **not** the load-bearing serialization state. Serialization correctness comes from the conflict-scan lease (above) plus the goal ledger (`held_conflict_keys` on the holder, the `conductor_run_queued` event on the waiter) — the goal ledger is the source of truth for who-is-deferred-behind-whom (Principle 1); the `enqueue()`d queue file is an audit breadcrumb + a demonstration of the spec/44 producer primitive, never the authoritative waiter registry. The advisory is written ONCE per (deferred-run, blocking-gate) pair: a re-poll short-circuits at the top-of-run queued-event check (`_find_queued_event`) and returns `status='deferred'` again *before* reaching the enqueue site, so the bucket does not grow per poll (and the file is never re-written — the single-write-per-pair claim, not a last-writer-wins overwrite path that never executes). A drain/consumer/reap for the advisory bucket is out of scope for PR3 (not load-bearing for correctness); it is tracked in #662.

**Self-release model.** On the next `run()` invocation, `_find_queued_event(history_path)` detects the outstanding `conductor_run_queued` event. `run()` then calls `_is_decision_still_pending(agent, decision_id, blocking_run_id)` to re-check the blocking gate. If the gate was answered (status no longer `awaiting_decision`), `run()` self-releases by appending `conductor_queue_released` and continues the stage loop (re-deriving `completed_stage_ids` from the durable goal, never reporting 0 progress for a run that completed automated stages before deferring). If the gate is still pending — or if the gate's status cannot be read (fail-closed: a transient read error keeps the waiter deferred rather than self-releasing it into the resource) — `run()` returns `status='deferred'` again (idempotent re-defer). `resume()` does NOT push-release deferred waiters; self-release on the next `run()` call is the contract.

**Honest limit — the hold spans the gate-SUSPENSION window, not the execution window.** Be precise about what `conflict_keys` does and does not mutually exclude. The holder owns the key only while its gate is **suspended**: `_record_gate_answer()` clears `held_conflict_keys` at gate-answer (`fields={'gate_decision_id': None, 'held_conflict_keys': []}`), so the moment the human answers A's gate, A no longer holds the key and the deferred run B becomes eligible on its next tick. This means A's **post-gate execution** and B's execution are **NOT** mutually excluded — both runs' post-gate stages for the same key can overlap in time. The serialization guarantee is "two runs do not sit *suspended* on the same key concurrently, and a new run does not *enter* a conflict-keyed gate while a holder is suspended on it"; it is **not** "only one run touches the protected resource at a time." If true execution-window exclusivity is required (only one run may run the protected work at once), the protected work must itself be a **gated stage** (so the second run defers behind the first run's gate for the whole window), or await a future execution-lock mechanism. PR3 does not implement execution-window locking; this limit is documented, not closed (Principle 13).

### expected_decision_id CAS at gate answer (H1 closed)

`_record_gate_answer()` now passes `expected_decision_id=decision_id` to the `apply_transition()` call. This inner-lock CAS (spec/41 MUST 14) prevents a stale or duplicate `resume()` from answering a gate that was already answered by a concurrent call that raced past the outer status check. If `sub_goal.gate_decision_id != decision_id` under the goal lock, `GoalConcurrentModification` is raised and nothing is written.

`_record_gate_answer()` also passes `fields={'gate_decision_id': None, 'held_conflict_keys': []}` to clear both fields on gate answer.

### ConductorState: status='deferred' and the queued-behind fields

`ConductorState` gains:
- `status` literal extended with `'deferred'` (alongside `complete`, `halted`, `awaiting_decision`). The value is `'deferred'`, NOT `'queued'`, to avoid colliding with the QueueBackend's own `queued/` queue-dir vocabulary (deferred-run-status-value ruling).
- `queued_behind_decision_id: str | None = None` field — which gate decision is blocking this run.
- `queued_behind_conductor_run_id: str | None = None` field — which conductor run holds that gate (the blocking gate lives in a DIFFERENT conductor run).
- `__post_init__` invariant: `status='deferred'` requires BOTH `queued_behind_decision_id` and `queued_behind_conductor_run_id` non-None; any other status requires both are None.

### New ledger events (append-only, not normative for GoalBackend)

Two new event names are appended to `goal_history.jsonl` by the conductor:
- `conductor_run_queued` — written when a conflict is detected. Fields: `ts`, `event`, `conductor_run_id`, `stage_id`, `blocking_decision_id`, `blocking_conductor_run_id`, `conflict_keys`.
- `conductor_queue_released` — written when self-release detects the blocking gate was answered. Fields: `ts`, `event`, `conductor_run_id`, `blocking_decision_id`, `blocking_conductor_run_id`.

These events are audit-only. `_sum_cumulative_spend()` does NOT count them (only `sub_goal_outcome_dispatched` events carry cost).

## Versioned normative addendum — #583 PR4 (2026-06-28): launder-guard upgrade + doctor check

This addendum records the implementation contracts shipped in PR4, which completes the arc and locks this spec.

### C7 launder-guard: warn → hard raise

`run()` and `resume()` now raise `ConductorLaunderRefused` (rather than emitting a `warnings.warn()`) when `agent.trigger == 'delegate'` is detected. The guard fires BEFORE any durable work in both functions:

- In `run()`: before `_resolve_or_create_run()` — no `goals/<id>/` directory is ever created for an invalid delegate call. No `conductor_run_started` event is emitted.
- In `resume()`: before the disposition/rationale validation, before the principal check, and before `_record_gate_answer()` — the gate sub-goal remains in `'awaiting_decision'` after the raise. No `conductor_gate_answered` event is emitted.

The exception class is `ConductorLaunderRefused(NestedDelegationRefused)` in `atomic_agents/exceptions.py`. It is NOT a subclass of `ConductorError` — this is a spec/15 one-level-delegation violation, not a transient orchestration error, and it must not be caught by any `except ConductorError` retry handler. It is exported from `atomic_agents` at the top level alongside `CostGuardrailBlocked` and `LockBusy` for consistent hard-guard signal import patterns.

The guard is keyed on the observable `trigger == 'delegate'` signal. Structural call-depth enforcement (refusing a launder when the trigger signal is absent) remains deferred to [#665](https://github.com/dep0we/atomic-agents-stack/issues/665). This closes the OD3 "best-effort guard for the obvious case" ruling for the raise-vs-warn question.

**Conformance tests:** TEST 45 (`run()` raises `ConductorLaunderRefused` when `trigger=='delegate'`, with ledger-empty negative control confirming no goal directory created) + TEST 45-strip-RED (non-delegate trigger does not raise) + TEST 46 (`resume()` raises BEFORE any ledger write, with byte-exact history-file comparison confirming `goal_history.jsonl` is unmodified and gate sub-goal remains `'awaiting_decision'`) + TEST 46-strip-RED (non-delegate trigger does not raise).

### check_conductor(agent_root) — orchestration-layer doctor check

`check_conductor(agent_root: Path) -> CheckResult` is wired into `run_doctor()` as an ORCHESTRATION-LAYER check (not a backend protocol check). It is positioned after `check_agent_registry_backend` in the agent-scoped execution block and labeled `'conductor'` in both the no-agent SKIP roster and the agent-scoped call.

**Dual-probe contract:**

1. **Light probe:** scans `goals/<id>/goal_history.jsonl` for `conductor_run_started` events across all goals directories. Identifies all conductor runs; selects the most recent by the `conductor_run_started` event's `ts` (fallback: the `goal_history.jsonl` file's mtime). Recency is **NOT** derived from the run_id — `_mint_conductor_run_id()` emits a random UUID4 (`crun-<uuid4().hex[:16]>`) with no temporal order, so a lexicographic run_id sort would probe an arbitrary run and could mask corruption in the genuinely-latest run.
2. **Heavy probe (STRICTLY READ-ONLY):** calls `get_default_goal_backend(agent_root).for_goal(run_id).load_goal()` on the most-recent run. Reads `goal_history.jsonl` via `_iter_history_events()` for the event-name set, honoring that reader's `ok=False` degraded signal (it swallows `OSError`/`JSONDecodeError` into `(rec, ok=False)` units and never raises). Checks: each `awaiting_decision` sub-goal carries a `gate_decision_id` (a missing one is durable cursor corruption — FAIL) AND has a `conductor_gate_pending` event matching its `stage_id` + `decision_id` (the per-gate matcher `_find_gate_pending_event`, not a coarse any-gate-pending check); each `skipped` sub-goal carries a recorded `conductor_gate_answered(disposition='skip')` ruling (a missing one is durable corruption — FAIL, via `_has_gate_answered_skip`, the symmetric partner of the awaiting-decision cursor FAIL; checked only when history is not degraded, since it reads the audit log); `complete` automated sub-goals have an `output` pointer. No write operations — no `append_history_event()`, no `apply_transition()`, no healing.

**PASS/WARN/FAIL ladder:**

- `PASS` with `conductor_runs_found: 0` when no conductor runs exist (clean state — NOT SKIP; the check ran and found a healthy empty set).
- `PASS` with run detail when the most-recent run's goal and history are readable and the cursor walk finds no anomalies.
- `WARN` for transient read exceptions (race between scan and load), unreadable `goal_history.jsonl` (the append-only AUDIT log, distinct from the `goal.md` state snapshot — the heavy probe detects the `ok=False` degraded signal, returns a `history_degraded` WARN, and SKIPS the cursor walk rather than running it against a partial event set and crying wolf about a missing `output` pointer / missing gate-pending audit), non-`AddressableGoalBackend` registrations, or cursor anomalies: a missing per-gate `conductor_gate_pending` event on a sub-goal that DOES carry its `gate_decision_id` self-heals on next `run()`; a missing `output` pointer on an **AUTOMATED** `complete` stage (an answered gate is NOT one — it is identified by its durable `conductor_gate_answered` audit and is exempt) is repaired by `resume()` from a COMPLETED idempotency record **IF one resolves, otherwise it fails closed as `GoalCorrupted` per the C2 predicate (§120)**. The probe cannot cheaply consult idempotency, so it WARNs (not a guaranteed self-heal); the recovery vs. fail-closed outcome is decided by `resume()`.
- `FAIL` for confirmed `goal.md` state-snapshot corruption surfaced during `load_goal()` — both `GoalCorrupted` (unparseable `goal.md`) AND `SchemaValidationError` (parseable-but-schema-invalid frontmatter: duplicate `sub_goal` id, missing required field, bad `schema_version`, broken `blocked_by` graph; NOT a `GoalCorrupted` subclass, caught explicitly so it does not fall through to a transient WARN). Also `FAIL` for an `awaiting_decision` sub-goal carrying NO `gate_decision_id` — `run.py` raises `GoalCorrupted` for exactly that state (the durable resume cursor is unreadable), so the next `run()`/`resume()` hard-fails; the probe mirrors that rather than under-reporting it as a healable WARN. Also `FAIL` for a `skipped` sub-goal carrying NO recorded `conductor_gate_answered(disposition='skip')` ruling — `run.py:660` raises `GoalCorrupted` for exactly that state (spec/50 C4 "a skipped stage is a recorded ruling, never an absent stage"; a skipped stage sits behind the resume frontier, so the next `run()`/`resume()` iterates to it first and hard-crashes), so it is durable corruption, not a healable WARN. This is the fourth hard-crash class, symmetric with the awaiting-decision cursor FAIL; because it reads the audit log it is guarded behind the `history_degraded` WARN (a truncated audit log cannot confirm the ruling and WARNs rather than false-FAILing). **Out-of-scope false-PASS (named honestly):** a present-but-dangling `output` pointer on an automated `complete` stage (a `result_ref` that no longer resolves via `OutcomeBackend.read_result`) hard-crashes `resume()` as `GoalCorrupted`, but confirming store-resolvability needs `OutcomeBackend` store I/O — the expensive path this read-only cursor probe deliberately avoids — so the probe validates pointer **presence**, not resolvability, and returns `PASS`; `run.py`'s C2 fail-closed predicate is the runtime backstop.

`SKIP` is emitted ONLY by the no-agent SKIP roster (when `run_doctor(agent_name=None)` runs without `--agent`).
