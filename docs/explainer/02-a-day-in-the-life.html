Chapter 02

A day in the life

What actually happens when you ask an atomic agent to do something. We'll follow Scout — a research-assistant agent — through a single task, watching exactly which files get read, what gets thought, and what gets written back.

The setup

Imagine you open your terminal and type:

uv run atomic-agents run scout --work-item "Find three articles about agentic memory and summarize the consensus."

That command kicks off a single "run" of the Scout agent. Roughly nine seconds later, the run finishes with a written summary and three new memory notes. Let's slow that nine seconds down.

The full lifecycle of a single agent run. Most steps are invisible to you; you just see the final response.

Let's walk through what each step actually does.

Step 1 — Load the files

The runtime opens Scout's folder and reads, in order:

  • persona/IDENTITY.md, SOUL.md, USER.md — the binders explaining who Scout is, what voice she uses, and who Dan is.
  • model.md — which language model to call (e.g., Claude Sonnet 4.6) and what the daily/monthly spending caps are.
  • tools.md — what files Scout can read, what websites she can call, what she's forbidden to touch.
  • memory/INDEX.md — a small (typically under 2,000 words) index of all the memory notes. Not the notes themselves yet — just a routing sheet that says "if the topic involves Dan's preferences, look at user_dan_*.md; if it involves Q3 work, see project_q3_*.md."
  • journal/2026-05-16.md — yesterday's narrative summary (gives Scout continuity).
  • goal.md (if present) — the long-running thing she's working toward.

Step 2 — Cost check

Before sending anything to the language model (which costs money per call), the runtime checks: have we already spent today's budget? If Scout's model.md says "$5/day cap" and she's already used $4.80, the runtime refuses to start the call and tells you. No surprise bills. We'll go deeper on this in Chapter 3.

Step 3 — Assemble the system prompt

The "system prompt" is a single big block of text that gets handed to the language model. The runtime concatenates the loaded files in a deliberate order — identity first, then user context, then capabilities (tools), then memory routing layer, then yesterday's journal, then your task. The order matters because language models pay more attention to what comes earlier.

A subtle but important point

Scout's "memory" isn't all loaded into the prompt. Only the INDEX is — a couple thousand words that tell the model what notes exist. The full notes get loaded later, only the specific ones the model decides it needs. This keeps the prompt small and focused (and cheap).

Step 4–5 — Off to the language model

The prompt plus your task ("Find three articles about agentic memory…") goes to the language model — Claude, GPT-5, Kimi, whichever Scout's model.md specified. The model reads everything and decides: do I have enough information to answer, or do I need to call a tool first?

Step 6 — Tool calls (or final answer)

The model might say: "I need to fetch this URL" or "Let me search the web for that" or "Open this note in memory." Each request comes back as a structured tool call.

If there are no tool calls — the model has the answer already — we jump straight to step 9. Most non-trivial runs go through several tool-call cycles, though.

Step 7 — The judge reviews

For risky actions — sending an email, writing to a sensitive folder, calling an external API — a separate "judge" inspects the tool call before it executes. Read-only actions (like loading a memory note) skip this step. The judge can ALLOW, BLOCK, REVISE (suggest an amendment), or ESCALATE to you for approval. Chapter 3 covers this in detail.

Step 8 — Execute, then loop

Approved tool calls run. Their results (the article text, the search results, the contents of a memory note) get fed back to the language model, and we loop back to step 5. The model thinks again with the new information, possibly requests more tools, and so on — usually three to ten rounds — until it has a final answer.

Step 9 — Extract new memories

When the model produces its final response, the runtime scans it for special markers — little fenced blocks where the model has indicated "this is worth remembering." Each marker becomes a new atomic note file in memory/. For our example:

memory/reference_agentic_memory_consensus.md
memory/reference_letta_paper_2024.md
memory/decision_use_index_driven_recall.md

Step 10 — Write everything down

The runtime writes the new memory notes, appends a paragraph to journal/2026-05-17.md, and writes a single structured line to log/2026-05/2026-05-17.jsonl capturing the precise mechanics — what model was used, how many tokens, what tools were called, how much it cost, how long it took.

Crash-safe by construction

Every write happens with a careful pattern called temp file + fsync + rename + parent-dir fsync. If the power goes out mid-run, you don't get a corrupted note — you get either the old version or the new version, never a half-written file. This is the same technique databases use for durability.

How memory actually works

Memory is the part most people find surprising. There's no database, no vector store, no embedding magic by default — just text files arranged in three layers.

Three memory layers with different purposes — and different loading strategies.

Atomic notes — one fact per file

The note "Dan prefers concise responses" lives in its own small file (memory/user_dan_prefers_concise.md). The note about the Q3 deadline lives in a different file. The note about which database we chose lives in a third. There are five canonical types: feedback, decision, project, reference, user. Each note has a tiny header (frontmatter) saying its type, confidence, date — then a paragraph of plain prose.

Why one fact per file? Because facts get edited independently. If you want to update what Scout knows about Dan, you can find and fix the single file without touching anything else.

INDEX — the routing layer

If Scout has 200 atomic notes, loading them all into the prompt would be expensive and noisy. Instead, memory/INDEX.md contains a compressed map: short titles, types, and one-line summaries of every note. The language model reads the INDEX (cheap), decides which 1–3 notes it actually needs for the current task, then asks the runtime to load those specific files (also cheap). This is called INDEX-driven recall.

Wiki — the distilled library

Over time, many small atomic notes about the same topic accumulate. The wiki is where they get consolidated into longer, more polished articles. For example: ten atomic notes about Dan's communication style might consolidate into one wiki article called wiki/communication-style.md. The consolidation happens during "dreaming" — we'll cover that in Chapter 4.

What gets written down — the audit trail

Every single thing the agent does is logged. Not just the final answer — every step, every tool call, every cost, every judge decision. Open log/2026-05-17.jsonl after a run and you'll see something like:

{"run_id": "r-abc123", "ts": "2026-05-17T09:15:32Z", "agent": "scout",
 "model": "claude-sonnet-4-6", "tokens_in": 4287, "tokens_out": 1402,
 "cost_usd": 0.041, "tool_calls": 4, "duration_s": 8.7, "outcome": "ok"}

If Scout delegated to another agent during the run, the delegate's run gets its own line linked back to the parent via parent_run_id. If Scout called a helper (a cheaper sub-model for a small task), that's logged too. There's no hidden behavior. You can read every decision Scout made yesterday by reading yesterday's log.

Why "JSONL"?

JSONL = "JSON Lines" = one structured record per line of a text file. You can grep it, you can pipe it through tools like jq, you can open it in any spreadsheet. It's just text, but text with a precise shape. The framework's dashboard reads these files to render cost charts.

Putting it together

That's the daily routine of an atomic agent: load files → check cost → ask the language model → execute approved actions → write new memories → log everything. The folder grows a little richer every time you ask Scout to do something. Tomorrow's Scout knows everything today's Scout learned — because tomorrow's Scout opens the same folder.

Next, we'll look at the safety net that sits in front of every action: the judge layer that decides what Scout is allowed to do, and the cost guardrails that decide how much she's allowed to spend.
