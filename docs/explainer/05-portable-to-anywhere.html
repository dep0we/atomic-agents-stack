Chapter 05

Portable to anywhere

A person at home with one agent and a company with fifty agents should not need different software. Atomic Agents achieves that with a pattern called protocols — a set of standardized interfaces that let the storage underneath the agent be swapped without changing the agent itself.

The challenge

Everything we've covered so far assumes the agent's data lives in a folder on a single computer. That works wonderfully for one person with one agent — which is the primary shape the framework is designed for.

But the same framework has to also work when:

  • The agent is part of an internal tool used by twenty people, where everyone's edits to the persona need to sync.
  • The agent runs on three identical servers behind a load balancer, all reading the same memory and writing the same logs.
  • The agent's logs need to ship to a centralized monitoring system instead of sitting in JSONL files.
  • The agent's tool catalog comes from a company-internal "tool store" with audit and approval, not just files on disk.

The naive answer would be: "fork the framework, swap the file reads for database reads, deal with the merge pain forever." That's how most frameworks scale — by giving up portability when you outgrow the laptop. Atomic Agents takes a different path.

Protocols — the moat

A protocol, in this framework's vocabulary, is a precisely-specified interface for a single concern. Each protocol has:

  1. A spec document — a numbered markdown file describing what the protocol promises (e.g., docs/spec/22-log-backend.md).
  2. A reference implementation — a default that uses your filesystem. Free, no setup, works for one person on one laptop.
  3. A conformance test suite — a battery of tests that any implementation must pass. This is the actual contract.
  4. An implementer contract — a short list of must-have behaviors any new implementation has to honor.

The agent itself doesn't know or care which implementation it's using. It calls the protocol; the framework dispatches to whichever backend is registered. Swap the backend at deployment time via a single environment variable, and the agent is suddenly running over Postgres, or Redis, or a remote HTTP service — without any change to the agent's folder or behavior.

The eight shipped protocols

Today, eight protocols are locked and in production. Each closes one specific scaling cliff.

MemoryBackend — atomic notes, INDEX, wiki, capture flow.
Default: filesystem (the memory/ folder you've already seen). Future implementations could store memory in a vector database for semantic search at scale.
LLMBackend — the call to the language model itself.
Ships with three reference implementations: Anthropic (Claude), OpenAI (GPT family), and Moonshot (Kimi). Adding a fourth (Gemini, vLLM-local, Bedrock) is a single registration call — no fork needed.
JudgeBackend — the safety layer from Chapter 3.
Ships with a rule-engine judge (fast, free) and an LLM-judge (slower, smarter). You configure which judge handles which action class in judges.md.
LockBackend — prevents two copies of the same agent from clobbering each other.
Default: a per-file lock on disk (POSIX flock) — works fine for one host. Alternative: Redis-based advisory locks for multi-host deployments where different servers might run the same agent.
LogBackend — where the audit trail goes.
Default: JSONL files (one per day per agent). Alternative: a SQLite database with indexed queries for dashboards that need to answer "show me all the high-cost runs this week" in milliseconds instead of scanning thousands of JSONL lines.
AgentProfileBackend — the bootstrap (persona, tools, model, judges, MCP, goal).
Default: walks the folder, reads each file. Alternative: load from a SQLite database — required for SaaS deployments where the persona is editable through a web UI.
ToolRegistryBackend — the catalog of installable tools.
Default: walks <agent>/tools/ for markdown descriptors and Python handlers. Alternative: SQLite-backed catalog with cross-tenant isolation, used for plugin-marketplace shapes where tools come from a central registry with audit and approval.
MandateBackend — durable revocable scoped authority for actions that touch real money or external side effects.
Operators author a mandates.md file granting agents specific authority (e.g., "spend up to $6,000 cumulatively on the Q2 ad campaign"). The framework defends that cap against concurrent runs and crash-restart, and surfaces audit signals when an action's executed target diverges from what was authorized at proposal time.

What's still to come

Four protocols remain on the roadmap for v1.0:

PersonaBackend
Unlocks: UI-editable identity/soul/user, persona versioning, A/B testing different personas against the same eval suite.
CorpusBackend
Unlocks: wiki and raw knowledge at GB scale, semantic search, RAG retrieval — the things the filesystem MemoryBackend doesn't try to do.
PolicyBackend
Unlocks: org-level policy that supersedes per-agent settings. A company can enforce "no agent in this tenant may call the legal-document tool without escalation" centrally, without trusting each agent's local config.
MCPServerRegistryBackend
Unlocks: a catalog for MCP servers (external tool providers) parallel to what ToolRegistryBackend does for in-process tools.

v1.0 of the framework closes when all four ship with their own reference implementations and conformance suites. Eight-of-twelve is where we are today; twelve-of-twelve is the stable surface.

The home shape vs. the company shape

Here's the same agent — same folder, same persona, same tools, same judge config — running in two very different deployments. Notice what changes and what doesn't.

🏠 The home shape

  • Folder on your laptop
  • Filesystem MemoryBackend
  • Filesystem LogBackend
  • POSIX-lock LockBackend
  • Filesystem ProfileBackend
  • Filesystem ToolRegistry
  • Filesystem MandateBackend (off by default — opt-in via mandates.md)
  • Anthropic LLMBackend
  • Rule-engine JudgeBackend
  • One agent, one folder, zero servers

🏢 The company shape

  • Same folder layout — possibly on shared storage
  • Filesystem MemoryBackend (same)
  • SQLite LogBackend (indexed dashboards)
  • Redis LockBackend (multi-host coordination)
  • SQLite ProfileBackend (UI-editable)
  • SQLite ToolRegistry (audit + install approval)
  • Filesystem MandateBackend (same — v1 ships filesystem-only; SaaS/DB seam in place)
  • Anthropic LLMBackend (same)
  • LLM JudgeBackend (smarter review)
  • Same agent — different substrate underneath

The home user opens the folder in Obsidian and reads the journal. The company runs the same agent across three Cloud Run instances behind a load balancer, with logs flowing to a dashboard that answers "show me all escalations from this team this quarter" in milliseconds. The agent's persona doesn't know which world it's in. The agent's tools don't know. The agent's memory doesn't know. The only difference is what's registered as the backend for each protocol. (MandateBackend is the one shipped protocol where v1 only includes the filesystem reference impl — the Protocol seam ships from day one so future SaaS / mobile / Slack-bot adapters slot in via register_mandate_backend() without forking core.)

How the swap actually happens

Concretely, switching from filesystem-everything to SQLite-for-logs looks like setting one environment variable:

export ATOMIC_AGENTS_LOG_BACKEND=sqlite
export ATOMIC_AGENTS_LOG_BACKEND_URL=sqlite:///shared/logs.db
uv run atomic-agents run scout --work-item "Daily morning brief"

That's it. The agent's folder doesn't change. The agent's persona doesn't change. The runtime sees the env var, dispatches log writes to SQLite, and everything else continues as before. Tomorrow you can flip it back. Next month you can flip Profile to SQLite too. The home user has none of these env vars set; they get the filesystem defaults and never need to think about it.

The conformance suite is the actual moat

Anyone — a third party, a company integrating internally, you in a year — can write a new backend. They drop their implementation into the conformance test harness. If the tests pass, their backend is fully interoperable with everything else. If the tests fail, they know exactly which guarantees they're violating. The framework isn't trying to ship every possible backend itself; it's trying to be a contract that other backends can plug into.

Why this matters for a non-developer

You probably won't write a new backend. You probably won't deploy across three Cloud Run instances. So why care about all this?

Two reasons:

  1. Your agent is portable forever. If a year from now you want to move from Anthropic's Claude to a different language model, the agent doesn't change — just the LLMBackend. If you want to move from filesystem logs to a cloud monitoring tool, the agent doesn't change — just the LogBackend. The shape you depend on (the folder, the markdown files, the persona, the memory) is the layer that never moves.
  2. The framework is not a vendor lock-in. The spec documents are public. The reference implementations are MIT-licensed. Anyone can build a conforming runtime in any language. The atomic agent in your folder doesn't depend on this Python project surviving — it depends on the spec surviving. If the maintainer disappears, your agent still works because the spec is the product.

The folder is the agent. The spec is the contract. The backends are the substrate. Same agent, every scale.

That's the framework. Plain markdown files for what the agent is. Protocols for what the agent depends on. A spec for what every implementation must promise. A reference implementation that's the default. And the freedom to swap any layer underneath without disturbing the one above.

For most people, "the layer above" is enough. Open Obsidian. Edit a persona. Run a task. Read the journal. Watch the agent get sharper week by week. The complicated machinery underneath is there if you ever need it — but you can use the framework for years without needing to.

One last thing — the spec is the product

Twenty-eight numbered spec documents (plus three in-progress drafts) describe the framework in precise detail. The Python code in this repository is one implementation of that spec. Eventually there will be others — in different languages, with different optimizations, integrated into different tools. What you build on top of this framework doesn't depend on any one of them. It depends on the shape.
