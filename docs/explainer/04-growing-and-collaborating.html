Chapter 04

Growing and collaborating

An agent that only ever follows instructions doesn't really grow. Two features close that loop. Dreaming is a background process that periodically reviews and consolidates memory, making the agent smarter over time. Delegation lets agents call other agents — turning a single assistant into a focused team.

Dreaming — how an agent gets smarter

Every time Scout runs, she may write new atomic notes — a fact she learned, a decision she made, a preference she noticed. After a month of regular use, her memory/ folder might have a hundred notes. Some are still useful. Some duplicate each other. Some contradict each other. Some have aged out of relevance.

Without intervention, this accumulates into noise. The INDEX gets bigger; recall gets less precise; the agent's behavior becomes less coherent. The solution is a periodic background process called dream.

What dreaming actually does

A dream isn't mystical — it's a separate run mode that scans recent activity and reorganizes the memory layers. Specifically, during a dream Scout:

  1. Reviews recent atomic notes. Anything created since the last dream.
  2. Identifies patterns and duplicates. Three separate notes saying "Dan prefers concise replies" should become one canonical note (or a wiki entry).
  3. Consolidates into the wiki. Take a cluster of related atomic notes and write a longer, distilled wiki article that subsumes them. The atomic notes get tagged as "consolidated" or get archived; the wiki article becomes the new source of truth on that topic.
  4. Tightens the INDEX. Removes stale entries, updates summaries, keeps the routing layer small.
  5. Surfaces patterns worth your attention. If Scout noticed that three different projects have been blocked on the same dependency, she may write a note pointing this out.
  6. Updates the journal. A "what I dreamed about" entry, so you can scan it in the morning.

Why this matters

Without dreaming, an agent's memory is like a desk where every observation gets a fresh sticky note and nothing ever gets thrown away. Within weeks the desk is unusable.

With dreaming, the memory layer naturally tiers itself:

Fresh atomic notes
Recent observations, high signal-to-noise. Less than a week old. Loaded into context aggressively.
Wiki articles
Distilled, durable knowledge. Loaded on demand when the topic comes up.
Archived atomic notes
The raw observations that fed the wiki article. Still in the folder for audit ("what did Scout actually observe?") but no longer in the routing INDEX.

Dreaming is just another run

It uses the same runtime, the same language model, the same cost guardrails. It has its own budget (typically smaller — consolidation is cheap). It writes its own log lines. There's no separate "dream system." It's a job that runs nightly with a particular task: "review your recent activity and consolidate."

Delegation — turning one agent into a team

Some tasks are too big or too varied for a single agent. Writing a research report involves research (gathering facts), writing (drafting prose), and editing (polishing). Each of those is a different skill with different prompts, different tools, and different judges.

Atomic Agents handles this with delegation: one agent can call another agent as if it were a tool. The called agent runs in its own folder, with its own persona, its own memory, its own budget — but its run is tied to the parent's run via the audit log.

The one-level rule

The framework intentionally limits delegation to one level deep. The coordinator can call researcher, writer, and editor. Those specialists cannot delegate further — researcher can't call a sub-researcher to call a sub-sub-researcher.

This is a deliberate constraint, not a missing feature. Two-level (and deeper) delegation chains look like flexibility but produce unauditable trees: who called whom for what reason, with whose budget? The one-level rule keeps the call graph readable. If a specialist needs help, the framework expects it to ask the coordinator, which makes the decision visible.

In Apple terms: the same shape at every scale

One coordinator with three specialists, or one coordinator with thirty specialists — the structure is identical. The coordinator's job is orchestration; the specialists' job is focused execution. No level above, no level below. You always know where you are in the tree.

The tree-cap — running a team isn't a bankruptcy event

The cost guardrails from Chapter 3 extend to delegation in an important way. When the coordinator delegates to a specialist, the specialist's budget is capped to the minimum of (the specialist's own daily cap) and (the coordinator's remaining budget for this run).

Concretely: if the coordinator has $5/day and has already spent $1.20 this morning, all the delegates today combined are capped at $3.80. The whole team shares the parent's pool. You can't trigger one expensive task that explodes into ten parallel expensive sub-tasks. The math is bounded.

Each delegate gets a budget capped by the parent's remaining pool. The team can't spend more than the parent had to give.

The roster — who knows whom

The coordinator's folder includes a roster.md file listing the agents it knows about and what each one is good for:

# Roster

- researcher — gathers facts, cites sources, scans recent papers
- writer — drafts prose in our standard voice
- editor — proofreads, tightens, checks claims against sources

When the coordinator's language model decides "I need help researching this," it consults the roster to figure out which delegate to call. The roster is just a markdown bulleted list — readable by you, editable by you.

The project layout — multiple agents on a shared mission

For larger work, the framework supports a "project" layout where multiple agents share some context but each have their own persona and memory:

~/agents/scout-project/ ├── canon.md# shared knowledge all roles read ├── style_guide.md# shared writing/output conventions ├── policy.md# shared rules (e.g., 'never cite Wikipedia') ├── judges.md# project-level safety floor └── agents/ ├── coordinator/ ├── researcher/ ├── writer/ └── editor/

When an agent inside the project runs, the runtime cascades its config — the role's own settings layered on top of the project's shared defaults. The researcher inherits the project's tools, style guide, and judge policy, and adds their own role-specific persona. The project-floor judges.md means even if a specialist's own config is lax, the project's safety rules can't be relaxed below the floor.

Putting it together

Dreaming is how an individual agent gets sharper over time. Delegation is how multiple agents become a team. Together they cover the two main growth paths:

Dreaming → depth

Scout, used regularly, develops nuanced understanding of you and your work. Her wiki grows. Her INDEX stays clean. After three months she's noticeably more useful than after one week.

Delegation → breadth

For tasks bigger than one agent can handle well, a coordinator dispatches to specialists who each do their part well. The call graph is auditable. The cost is bounded.

Both follow the same shape as everything else in the framework: more files in the folder. Dreaming writes new wiki articles. Delegation writes child run logs that link to the parent. The folder stays the source of truth, and you can read every step of the growth.

No magic, just persistence and orchestration

An agent doesn't "learn" in a machine-learning sense — the language model itself doesn't get retrained. Instead, the agent's folder accumulates better-organized knowledge over time. When you ask Scout something tomorrow, the language model reads a cleaner, more relevant memory layer than it did yesterday. The agent's "growth" is the folder's improving quality.

One topic remains: how does the same agent run unchanged from your laptop to a company-scale deployment? That's the protocol-pattern story, and it's the final chapter.
