Chapter 03

Safety and judgment

An AI assistant that can take real action — send emails, write files, spend money — needs guardrails. Atomic Agents has two: a "judge" that reviews risky actions before they happen, and cost caps that stop runaway spending. Both are configured in plain markdown.

The problem we're solving

Language models are clever but not infallible. They occasionally misread a situation. They occasionally hallucinate confidence. They have no sense of what a dollar costs you. Left alone with the ability to take real-world action, even a well-intentioned agent will eventually do something you didn't want — send the wrong email, overwrite a file you needed, rack up a $200 bill chasing a bad hypothesis.

Atomic Agents addresses this with two independent safety layers:

  1. The judge layer — a separate review step that gates risky actions before they happen, with four possible outcomes: allow, block, revise, or escalate to you.
  2. Cost guardrails — daily and monthly spending caps, with threshold warnings at 50%, 80%, and 100%.

Both are opt-in. Your agent runs without them just fine for low-stakes work. You turn them on when the stakes warrant — and you configure their strictness yourself, per agent, in markdown.

The judge layer

Before any side-effectful action runs — sending an email, modifying a file, calling an external API — the framework hands the proposed action to a "judge." The judge is a separate AI (or, for cheap simple checks, a rule engine) whose only job is to look at this single action and decide what to do.

The four action classes

Every tool an agent can use is tagged with one of four classes in tools.md:

read_only Reading a memory note, loading a wiki article, fetching a public web page.
No side effects. The judge is bypassed entirely — running the judge would add latency and cost for no safety gain.
reversible_write Saving a new memory note, updating the journal, appending a log line.
Side-effectful but recoverable. By default the judge runs and writes its opinion to the audit log, but the action is allowed regardless. You see "the judge had thoughts" without the judge being able to block you.
external_side_effect Sending an email, posting to a webhook, calling a paid API.
This is where the judge's opinion actually gates execution. Default policy is "judge required" — the action runs only if the judge returns ALLOW.
high_risk Deleting many files, spending money over a threshold, anything irreversible.
Always escalates to you, regardless of what the judge thinks. The agent pauses; the framework writes a PENDING file to vault/escalations/; you review and approve in your text editor.

The four outcomes

When the judge runs, it can produce one of four outcomes:

ALLOW — looks fine, proceed.
The action runs as proposed. The judgment is still logged so you have a record.
BLOCK — refuses to run this action.
The action is dropped. The reason is written to the audit log and surfaced in the run's response so the agent (and you) know what happened.
REVISE — proposes an amendment.
The most interesting outcome. The judge might say: "Send this email, but strip the attachment." or "Open the PR as draft, not for merge." The framework merges the amendment into the proposal, re-runs the judge once (so revisions don't loop forever), and if the second judgment ALLOWs, executes the amended version.
ESCALATE — kicks it up to you.
The agent writes a PENDING file describing the action; the run pauses; you go review it. We'll look at that flow next.

The escalation queue — where you come in

When something escalates, the framework creates a file like:

~/agents/scout/vault/escalations/high_risk/p-abc123.md

You open it in your editor (Obsidian, vim, VS Code, anything). The file shows the proposed action, the judge's reason, and a small set of instructions. You scroll to the bottom and add exactly one resolution block:

### Approved by dan
resolved_at: 2026-05-17T09:14:22Z
note: Reviewed — the email is correct, the recipients are right.

That's it. The next time Scout runs (or the next time you ask her to "check pending"), she sees the resolution, verifies the proposal hasn't been tampered with, and executes the approved action. There are five resolution verbs: Approved, Denied, Redacted, Revised (you write an amendment yourself), and Auto-decided (after a timeout, the framework picks for you per a configured policy).

Why a markdown file, not a dialog box?

Because the markdown file is part of the audit trail. There's no separate "approval database." Six months from now if you need to know who approved what, the answer is in your folder — same as everything else.

Configuring the judge — judges.md

The whole judge layer is opt-in. To activate it, drop a file called judges.md into the agent folder. The minimum viable version is just:

backend: rules
class_policy:
  read_only: bypass
  reversible_write: allow_with_audit
  external_side_effect: judge_required
  high_risk: escalate

That's the four default behaviors above. You can be stricter (read_only: judge_required means even loading a note gets reviewed). You can be looser (external_side_effect: allow_with_audit means external calls run, but with a log of the judge's thoughts). The strictness ordering is fixed: bypass < allow_with_audit < judge_required < escalate.

For multi-agent projects, a judges.md dropped at the project root acts as a floor — individual agents can be stricter than the floor, but can't be looser. A coordinator can ensure no specialist in the team ever runs a high-risk action without escalating, regardless of what the specialist's own config says.

Cost guardrails — model.md

The second safety layer addresses spend, not safety per se. Every LLM call costs money (typically pennies to dollars depending on the model and the prompt size). Without guardrails, an agent in a loop could rack up significant charges before you notice.

Each agent's model.md file has a structured block that sets caps:

cost_guardrails:
  daily_cap_usd: 5.00
  monthly_cap_usd: 100.00
  thresholds:
    warn_at: 0.5    # log a warning at 50% used
    alert_at: 0.8   # send an alert at 80%
    cap_action: stop  # at 100%, what to do: stop | log | alert

Before every language-model call, the runtime checks current cumulative spend. The behavior depends on where you are:

A four-zone meter — green to red — that the runtime checks before every model call.

Three things worth knowing about cost guardrails:

  1. They check before the call. The check happens before any tokens are billed. If you're at 100%, the runtime refuses to start; you don't pay for the discovery.
  2. They re-check every iteration. A complex run might bounce between the language model and tools five or ten times. Each iteration re-checks the budget — so a runaway loop catches itself instead of accelerating.
  3. Delegation is tree-capped. When one agent delegates to another (covered in the next chapter), the delegate's budget is capped to the parent's remaining budget. A coordinator running a team of five specialists doesn't get five copies of the daily cap — the whole team shares the parent's leftover budget. This is what makes "running an army" not a financial event.

The "critical" escape hatch

Sometimes you really do want an action to proceed even past the cap — an urgent customer reply, say. The API has a critical=True flag you can pass to bypass the check on a single call. The flag exists, but it's deliberately not the default. You have to ask for it, every time, in code. The framework's design refuses to make irresponsible spending easy.

How the two safety layers work together

The judge layer asks "should this action be taken?" The cost layer asks "can we afford to think about this any longer?" They're independent — turning one on doesn't require turning the other on — but they're complementary.

Judge layer protects against:

Sending the wrong email. Writing to a sensitive file. Calling an API with bad parameters. Taking an irreversible action you'd regret.

Cost layer protects against:

A runaway loop spending money. An expensive model used by mistake. A long-running task consuming the month's budget in an hour. Forgetting an agent is even running.

Together, they let you give your agent real capabilities — not just "summarize this article," but "send the weekly update to the team" — while keeping the failure surface bounded. The judge keeps actions correct; the cost cap keeps the exploration bounded.

The audit trail closes the loop

Both layers feed the audit trail. Every judgment writes a log line. Every cost-threshold crossing writes a log line. Every escalation writes a markdown file. When you come back tomorrow and want to understand "why did Scout refuse to send that email?" — the answer is in the log, written in plain English. No hidden behavior, no support ticket required.
